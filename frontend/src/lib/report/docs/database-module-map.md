# نقشه‌ی ماژول‌های دیتابیس (Schema Directory)

این فایل یک نمای کلی از **کل دیتابیس** (نرم‌افزار جامع مالی/اداری/تردد/انبار) است — نه جزئیات هر جدول.
هدف: قبل از شروع کار روی یک گزارش جدید، سریع بفهمی این کار به کدام ماژول/schema مربوط است و آیا آن
ماژول قبلاً کاوش شده یا باید مرحله‌ی ۰ (کشف دیتابیس) را برایش اجرا کنی.

منبع: خروجی واقعی `Full_Database_Discovery.sql` روی دیتابیس کاربر (تاریخ کاوش: تیر ۱۴۰۵ / ژوئیه ۲۰۲۶).
کل دیتابیس: **۳۷ schema، ۳۴۲۸ جدول**.

## فهرست schemaها (به ترتیب حجم داده، بزرگ‌ترین اول)

**به‌روزرسانی:** ساختار ستونی خام (نام/نوع/nullable/PK/روابط FK) همه‌ی ۳۷ schema اکنون در `references/schemas/<SCHEMA>.md` مستند است — دیگر برای «چه ستون‌هایی دارد» نیازی به کوئری تشخیصی نیست. آنچه هنوز برای schemaهای غیر از HCM3 مستند نشده، **معنای تجاری/semantic** ستون‌هاست (این فلگ یعنی چه، این جدول ledger است یا snapshot) — آن را فقط وقتی یک گزارش واقعاً به آن نیاز داشت، با نمونه‌داده/توزیع مقدار (طبق «مرحله ۰») بساز، نه از قبل حدس بزن.

**به‌روزرسانی دوم (تیر ۱۴۰۵):** لایه‌ی «سرنخ معنایی» `references/glossary/*.csv` هم اضافه شد (جزئیات کامل هر فایل در `references/persian-glossary.md`) — همین باعث شد ستون «معنای تجاری» جدول زیر برای ۹ schema از «کاوش‌نشده» به «سرنخ جزئی موجود» تغییر کند؛ هنوز جایگزین اثبات با نمونه‌داده نیست.

## قانون کار با این نقشه

- ساختار خام (ستون‌ها/نوع‌ها/PK/FK) همه‌ی ۳۷ schema از قبل در `references/schemas/<SCHEMA>.md` هست — دیگر لازم نیست برای «این جدول چه ستون‌هایی دارد» کوئری تشخیصی بسازی؛ مستقیم از آن‌جا بگیر (با `grep`, نه `view` کامل چون فایل‌ها بزرگ‌اند).
- آنچه هنوز مستند نیست **معنای تجاری** است: این فلگ یعنی چه، این جدول snapshot است یا ledger، کدام ستون کلید اصلی «فعلی/معتبر» را نشان می‌دهد. این را حدس نزن — وقتی گزارشی واقعاً به یک جدول ناآشنا نیاز پیدا کرد، طبق الگوی مرحله‌ی ۰ (`schema-discovery-queries.md`) فقط برای همان جدول‌های مشخص، نمونه‌داده + توزیع مقدار بخواه (نیازی به کاوش کل schema نیست، فقط جدول‌های مرتبط با آن گزارش).
- بعد از هر کشف معنایی جدید در یک schema، هم این فایل (ستون «معنای تجاری») و هم `known-database-schema.md` را به‌روزرسانی کن — دقیقاً مثل کاری که برای HCM3 انجام شد.
- schemaهای با ردیف صفر یا خیلی‌کم را در اولویت آخر بگذار — به‌احتمال زیاد ماژول‌هایی هستند که خریداری شده ولی هنوز در عمل استفاده نمی‌شوند؛ اگر گزارشی به آن‌ها نیاز پیدا کرد، اول از کاربر بپرس آیا واقعاً این ماژول در حال استفاده است.
