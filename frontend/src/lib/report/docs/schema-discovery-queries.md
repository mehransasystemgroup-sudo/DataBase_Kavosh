# الگوهای کوئری تشخیصی برای شناخت دیتابیس واقعی (مرحله ۰)

این فایل الگوهای آماده‌ی T-SQL را نگه می‌دارد که برای ساخت اسکریپت تشخیصیِ مرحله‌ی ۰ استفاده می‌شوند.
هدف: قبل از نوشتن کوئری نهایی یا ویرایش RDL، دقیقاً بفهمیم جدول‌های واقعی دیتابیس کاربر چه شکلی هستند —
نه با حدس زدن از روی اسم ستون‌ها.

هر بار که برای یک یا چند جدول جدید نیاز به این اطلاعات داری، این چهار بلوک را برای **هر جدول** بساز و
همه را در یک اسکریپت `.sql` واحد و مرتب (با کامنت جداکننده برای هر جدول) بسته‌بندی کن.

## ۱) ساختار کامل ستون‌ها

```sql
SELECT
    c.ORDINAL_POSITION,
    c.COLUMN_NAME,
    c.DATA_TYPE,
    c.CHARACTER_MAXIMUM_LENGTH,
    c.IS_NULLABLE,
    c.COLUMN_DEFAULT
FROM INFORMATION_SCHEMA.COLUMNS c
WHERE c.TABLE_SCHEMA = '<schema>' AND c.TABLE_NAME = '<table>'
ORDER BY c.ORDINAL_POSITION;
```

چرا این کافی نیست به‌تنهایی: نوع داده و nullable بودن را نشان می‌دهد، اما **معنای واقعی مقدار** را نه
(مثلاً یک ستون `bit` می‌تواند `NULL` باشد بدون این‌که مشخص کند این NULL در عمل چقدر رخ می‌دهد).

## ۲) نمونه‌ی واقعی داده (حداقل ۲۰-۵۰ ردیف)

```sql
SELECT TOP 50 *
FROM <schema>.<table>
ORDER BY <بهترین ستون تاریخ/شناسه برای دیدن داده‌ی متنوع و اخیر> DESC;
```

قانون: هرگز به کاربر نگو «چند ردیف نمونه بفرست» بدون عدد مشخص — همیشه صراحتاً بگو **۲۰ تا ۵۰ ردیف**،
چون یک یا دو ردیف تصادفی می‌تواند گمراه‌کننده باشد (نمونه‌ی واقعی: ستون `Entrance` در یک ردیف نمونه
`NULL` بود، که به‌تنهایی نشان نمی‌داد این ستون به‌طور کلی قابل‌اتکا هست یا نه).

## ۳) توزیع مقادیر یک ستون فلگ/کد/enum

هر وقت منطق گزارش به یک ستون کد/فلگ/وضعیت وابسته است (مثل `Entrance`, `AttendanceStatusRef`,
`ScaleCode`, `MeasurementUnitCode`)، این کوئری را **همیشه** اضافه کن — این تنها راه اثبات (نه حدس) است:

```sql
SELECT
    <flag_column>,
    COUNT(*) AS Cnt
FROM <schema>.<table>
-- در صورت نیاز فیلتر روی بازه‌ی زمانی مرتبط یا وضعیت خاص:
-- WHERE AttendanceStatusRef = 2
GROUP BY <flag_column>
ORDER BY <flag_column>;
```

نکته‌ی تفسیر: اگر تعداد `NULL` صفر یا ناچیز بود، یعنی می‌توان با اطمینان کامل روی این ستون منطق نوشت
و نیازی به fallback نیست. اگر تعداد قابل‌توجهی `NULL` بود، باید یک منطق ترکیبی (اول فلگ، بعد fallback
برای NULLها) طراحی شود — دقیقاً همان الگویی که در `sql-patterns.md` برای زوج‌بندی ورود/خروج آمده.

## ۴) روابط کلید خارجی (وقتی JOIN جدید لازم است)

```sql
SELECT
    fk.name AS ForeignKeyName,
    tp.name AS ParentTable,
    cp.name AS ParentColumn,
    tr.name AS ReferencedTable,
    cr.name AS ReferencedColumn
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fkc ON fkc.constraint_object_id = fk.object_id
JOIN sys.tables tp ON tp.object_id = fkc.parent_object_id
JOIN sys.columns cp ON cp.object_id = tp.object_id AND cp.column_id = fkc.parent_column_id
JOIN sys.tables tr ON tr.object_id = fkc.referenced_object_id
JOIN sys.columns cr ON cr.object_id = tr.object_id AND cr.column_id = fkc.referenced_column_id
WHERE tp.name IN ('<table1>', '<table2>')
   OR tr.name IN ('<table1>', '<table2>');
```

## ۵) الگوی بسته‌بندی نهایی برای تحویل به کاربر

اسکریپت نهایی که به کاربر می‌دهی باید:
- یک فایل `.sql` مستقل و قابل‌اجرا در SSMS باشد (نه تکه‌های پراکنده در چت).
- برای هر جدول یک بخش با کامنت تیتر جدا داشته باشد (مثلاً `-- ===== جدول hcm3.AttendanceData =====`).
- شامل هر ۴ بلوک بالا باشد که مرتبط است (بلوک ۴ فقط اگر JOIN جدید لازم است).
- در انتها یک توضیح کوتاه (کامنت) داشته باشد که دقیقاً بگوید نتیجه‌ی هر کوئری برای چه تصمیمی استفاده
  خواهد شد — تا کاربر هم بفهمد چرا این اطلاعات لازم است، نه فقط اجرا کند و نتیجه را کورکورانه بفرستد.

## ۶) بعد از دریافت نتیجه از کاربر

- نتیجه را با فرض‌های فعلی کوئری/RDL مقایسه کن.
- اگر فرضی نقض شد، **صریحاً در پاسخ بگو** چه چیزی تغییر کرد و چرا (نمونه: «فرض قبلی این بود که تردد‌ها
  متناوب فرد=ورود/زوج=خروج هستند؛ داده‌ی واقعی نشان داد ستون `Entrance` وجود دارد و در بیشتر موارد پر
  می‌شود، پس منطق را به نفع استفاده از `Entrance` با fallback برای NULL بازنویسی کردم»).
- کوئری/RDL نهایی را متناسب با واقعیت جدید به‌روزرسانی و دوباره از چک‌لیست مرحله‌ی ۴ (اعتبارسنجی) رد کن.

## ۷) الگوی کشف کل دیتابیس یک‌جا (وقتی هدف، شخصی‌سازی کامل Skill برای کل دیتابیس است، نه یک گزارش خاص)

وقتی کاربر می‌خواهد کل ساختار یک دیتابیس بزرگ (چند schema/ماژول) را یک‌بار برای همیشه مستند کند، به‌جای
تکرار بلوک‌های ۱-۴ برای هر جدول جداگانه، یک اسکریپت واحد بساز که ۴ خروجی جدا تولید کند:

1. فهرست کامل schema/table + تعداد ردیف تقریبی هرکدام (`sys.tables` + `sys.partitions`).
2. ساختار کامل ستون‌های تمام جدول‌ها در یک نتیجه (نه جدول‌به‌جدول) — `sys.columns` + `sys.types` +
   فلگ Primary Key از `sys.indexes`/`sys.index_columns`.
3. تمام روابط Foreign Key در کل دیتابیس در یک نتیجه.
4. نمونه‌ی داده‌ی هر جدول — چون هر جدول ستون‌های متفاوتی دارد و نمی‌شود در یک نتیجه‌ی جدولی یکدست
   نشانشان داد، از `FOR JSON AUTO` استفاده کن تا خروجی هر جدول یک ردیف با یک ستون JSON فشرده باشد
   (`SchemaName, TableName, SampleDataJson`) — این‌طور کل دیتابیس در یک شیت اکسل قابل خروجی‌گیری است.
   ستون‌های حجیم/باینری (`varbinary(max)`, `image`, `xml`, `geography`) را از JSON کنار بگذار.

نمونه‌ی کامل این الگو در `Full_Database_Discovery.sql` (تحویل‌شده به کاربر) پیاده‌سازی شده — یک کپی
از آن را برای استفاده‌ی بعدی نگه‌دار، چون این الگو قابل‌استفاده‌ی مجدد برای هر دیتابیس بزرگ دیگری هم هست.

بعد از دریافت هر ۴ خروجی، `references/known-database-schema.md` را از نو با پوشش کامل همه‌ی
schemaها/ماژول‌های کشف‌شده بازنویسی کن (نه فقط بخش HCM3 که تا الان مستند شده بود).
