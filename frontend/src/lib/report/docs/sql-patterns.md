# الگوهای رایج T-SQL برای دیتاست‌های Report Builder

این گزارش‌ها معمولاً روی SQL Server 2019+ (از جمله 2022) اجرا می‌شوند و از الگوهای زیر زیاد استفاده می‌کنند. قبل از نوشتن کوئری جدید از صفر، ببین آیا یکی از این الگوها همان چیزی است که لازم داری.

## ۱. پیوت داینامیک ستون‌ها بر اساس یک جدول تنظیمات (Factor/Config Table)

وقتی تعداد و نام ستون‌های خروجی از یک جدول تنظیمات دیتابیس می‌آید (نه از قبل مشخص است)، این الگو استاندارد است:

```sql
DECLARE @cols NVARCHAR(MAX);
DECLARE @query NVARCHAR(MAX);

SELECT @cols = STRING_AGG(QUOTENAME(Title), ',')
FROM dbo.SomeFactorTable
WHERE ScaleCode = 1;   -- فیلتر روی نوع/دسته موردنظر

SET @query = N'
SELECT ...,
    df.' + @cols + N'
FROM ... 
LEFT JOIN (
    SELECT *
    FROM ( SELECT Key1, Key2, FactorTitle, Value FROM ... ) AS src
    PIVOT ( MAX(Value) FOR FactorTitle IN (' + @cols + N') ) AS pvt
) df ON df.Key1 = ...
';

EXEC sp_executesql @query, N'@Param1 INT, @Param2 DATE', @Param1, @Param2;
```

نکات:
- همیشه از `QUOTENAME` استفاده کن تا اسامی فارسی/دارای فاصله مشکل‌ساز نشوند.
- پارامترها را همیشه با `sp_executesql` و لیست پارامتر تایپ‌شده پاس بده، نه با concatenation مستقیم در متن کوئری (خطر SQL Injection و هم مشکلات escaping کوتیشن).
- داخل رشته‌ی پویا (بین `N'...'`)، کوتیشن تک باید دوبل شود: `''مثلاً این‌طور''`.

## ۲. تبدیل «رکوردهای نامحدود در روز» به «تعداد ثابت ستون» با ROW_NUMBER

مسئله‌ی رایج: یک رویداد (تردد، تراکنش، ثبت) ممکن است چند بار در یک بازه (روز/دوره) اتفاق بیفتد، ولی گزارش باید حداکثر N نمونه‌ی اول را در N جفت ستون نشان دهد (نه فقط اولین/آخرین، و نه یک ردیف نامحدود).

```sql
-- گام ۱: شماره‌گذاری رکوردها به تفکیک کلید (مثلاً کارمند+روز) بر اساس زمان
SELECT
    EntityKey,
    BucketKey,          -- مثلاً روز تقویمی
    EventDateTime,
    ROW_NUMBER() OVER (PARTITION BY EntityKey, BucketKey ORDER BY EventDateTime) AS rn
INTO #Numbered
FROM ...;

-- گام ۲: پیوت به تعداد ثابت (این‌جا حداکثر ۳ زوج ورود/خروج = ۶ رکورد)
SELECT
    EntityKey, BucketKey,
    MAX(CASE WHEN rn = 1 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS In1,
    MAX(CASE WHEN rn = 2 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS Out1,
    MAX(CASE WHEN rn = 3 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS In2,
    MAX(CASE WHEN rn = 4 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS Out2,
    MAX(CASE WHEN rn = 5 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS In3,
    MAX(CASE WHEN rn = 6 THEN FORMAT(EventDateTime, N'HH:mm', N'fa') END) AS Out3
INTO #Pairs
FROM #Numbered
GROUP BY EntityKey, BucketKey;
```

نکات مهم:
- اگر رکوردی برای `rn` مشخصی وجود نداشته باشد (مثلاً روزی فقط یک تردد دارد)، مقدار NULL می‌ماند → در گزارش خودبه‌خود سلول خالی نمایش داده می‌شود؛ نیازی به منطق اضافه برای «مخفی کردن» نیست.
- اگر تعداد رکوردهای واقعی بیشتر از N باشد (نادر ولی ممکن)، مقادیر مازاد به‌سکوت نادیده گرفته می‌شوند مگر صراحتاً از کاربر پرسیده شود که با آن‌ها چه کند (ادغام در ستون آخر، هشدار جداگانه، افزایش N).
- این جدول موقت را با `LEFT JOIN` به کوئری اصلی وصل کن تا روزهایی که اصلاً رکورد ندارند هم در خروجی بمانند (نه `INNER JOIN`).
- فرمت `FORMAT(x, N'HH:mm', N'fa')` اعداد را به فارسی (۰۸:۲۱) برمی‌گرداند؛ اگر گزارش انتظار ارقام لاتین دارد، `'fa'` را حذف کن یا `'en-US'` بگذار.

### ۲.۱ نسخه‌ی پیشرفته: وقتی یک ستون فلگ صریح ورود/خروج وجود دارد

فرض «فرد=ورود، زوج=خروج» بر مبنای ترتیب زمانی فقط زمانی درست است که **هیچ ستون دیگری** برای تشخیص نوع رکورد وجود نداشته باشد. **همیشه اول در ساختار جدول (مرحله‌ی ۰) بگرد ببین ستونی مثل `Entrance`, `InOutFlag`, `EventType`, `Direction` وجود دارد یا نه** — اگر وجود داشت، حتی اگر گاهی `NULL` باشد، آن را در اولویت اول بگذار و فقط برای رکوردهای `NULL` به فرد/زوج برگرد:

```sql
SELECT
    EntityKey, BucketKey, EventDateTime,
    CASE
        WHEN Entrance = 1 THEN 1
        WHEN Entrance = 0 THEN 0
        ELSE ROW_NUMBER() OVER (PARTITION BY EntityKey, BucketKey ORDER BY EventDateTime) % 2  -- fallback فقط برای NULL؛ فرد(۱،۳،۵..)=ورود→۱، زوج=خروج→۰
        -- ⚠️ نسخه‌ی قبلی این فرمول («1 - (rn % 2)») برعکس بود و رکورد فرد را خروج و زوج را ورود می‌شمرد.
        -- با داده‌ی واقعی (گزارش «تردد روزانه کارمند»، ۲۰۲۶/۰۸/۰۱) این خطا کشف و اصلاح شد — همیشه با شبیه‌سازی روی نمونه‌ی واقعی این فرمول را تست کن، حدس نزن.
    END AS IsIn
INTO #Classified
FROM ...;

-- سپس ورود و خروج را جدا از هم شماره‌گذاری کن (نه یک شماره‌گذاری مشترک):
SELECT *,
    ROW_NUMBER() OVER (PARTITION BY EntityKey, BucketKey, IsIn ORDER BY EventDateTime) AS TypeRank
INTO #Ranked
FROM #Classified;
```

چرا این بهتر از فرد/زوج ساده است: اگر کسی یک روز دو بار پشت‌سرهم «ورود» بزند (یادش برود خروج بزند) و بعد یک «خروج»، فرد/زوجِ صرفِ زمانی این را اشتباه به‌عنوان ورود۱/خروج۱/ورود۲ می‌خواند، در حالی‌که با فلگ صریح درست به‌عنوان ورود۱، ورود۲، خروج۱ طبقه‌بندی می‌شود.

**قبل از تصمیم بین این دو حالت، همیشه از کاربر بخواه توزیع مقادیر ستون فلگ را با `GROUP BY` چک کند** (به `references/schema-discovery-queries.md` نگاه کن) — اگر `NULL` عملاً صفر بود، می‌توان fallback را کلاً حذف و کوئری را ساده کرد.

### ۲.۲ رکورد خام دوقلو در یک لحظه‌ی دقیق (وقتی یک رکورد اصلاح می‌شود ولی رکورد قدیمی حذف نمی‌شود)

الگوی رایج دیگر در جدول‌های رویداد/تردد: وقتی یک رکورد بعداً **ویرایش** می‌شود (نه حذف)، بعضی سیستم‌ها به‌جای آپدیت درجا، یک رکورد جدید با همان `EventDateTime` دقیق اضافه می‌کنند و رکورد قدیمی را دست‌نخورده (یا فقط با فلگ باطل) نگه می‌دارند. اگر رکورد قدیمی مقدار فلگ طبقه‌بندی (مثل `Entrance`) را `NULL` داشته باشد ولی رکورد جدید مقدار صریح دارد، بدون حذف تکرار هر دو وارد شمارش می‌شوند و روز به‌هم می‌ریزد:

```sql
;WITH RawWithTwin AS (
    SELECT *,
        SUM(CASE WHEN FlagColumn IS NOT NULL THEN 1 ELSE 0 END)
            OVER (PARTITION BY EntityKey, EventDateTime) AS FlaggedTwinCount
    FROM SourceTable
    WHERE <فیلترهای معتبر بودن رکورد>
)
SELECT *
FROM RawWithTwin
WHERE NOT (FlagColumn IS NULL AND FlaggedTwinCount > 0);
-- اگر یک رکورد بدون فلگ (خام/قدیمی) دقیقاً هم‌زمان با یک رکورد دارای فلگ (جدید/اصلاح‌شده) باشد،
-- نسخه‌ی بدون فلگ حذف می‌شود. اگر همه‌ی رکوردهای یک لحظه فلگ نداشته باشند، هیچ‌کدام حذف نمی‌شوند
-- (چون آن‌جا واقعاً یک رویداد بدون طبقه‌بندی صریح است، نه یک جفتِ خام/اصلاح‌شده).
```

**نشانه‌ی این الگو:** در کوئری توزیع مقادیر (مرحله‌ی ۰)، تعداد رکوردهای `EntityKey + EventDateTime` تکراری بیشتر از حد انتظار است، یا کاربر می‌گوید «این رکورد را اصلاح کردم ولی هنوز...». همیشه با نمونه‌ی واقعی تأیید کن که این دقیقاً همان الگو است، نه یک رویداد راستین دوبار در یک لحظه.

### ۲.۳ فیلتر کردن نوع رکورد: از جدول Lookup بخوان، حدس نزن

اگر یک جدول رویداد (مثل تردد) چند **نوع** رکورد را در کنار هم نگه می‌دارد (مثلاً هم حضور واقعی، هم مرزهای مرخصی/ماموریت، در یک جدول با یک ستون `StatusRef`)، **هرگز فرض نکن یک فلگ «معتبر بودن» عمومی (مثل `Enabled=1`) به‌تنهایی یعنی «نوع درست»**. `Enabled` معمولاً فقط یعنی «باطل نشده»؛ رکوردهای انواع دیگر (مرخصی، ماموریت، ...) هم می‌توانند کاملاً معتبر و `Enabled=1` باشند، فقط از نوعی نیستند که گزارش می‌خواهد نشان دهد.

راه درست: خودِ جدول Lookup که ستون کد به آن FK دارد را کامل بخوان (`SELECT * FROM <LookupTable> ORDER BY <IDColumn>`) و عنوان فارسی هر کد را ببین — نه از روی این‌که «Enabled=1 است» و نه از روی حدسِ عنوان‌های `glossary/lookup-values.csv` (که فقط فهرست مقادیر ممکن است، نه نگاشت دقیق کد). نمونه‌ی واقعی این خطا و رفعش: `known-database-schema.md` بخش «جدول‌های تردد خام» (`AttendanceStatusRef`).

## ۳. ستون‌های پویا: مخفی کردن ستونی که در کل نتیجه هیچ داده‌ای ندارد (نه فقط در یک ردیف)

**تفاوت کلیدی با الگوی ۲:** الگوی ۲ یک *جفت* را در یک *ردیف* پنهان می‌کند (مثلاً کارمندی که آن روز فقط یک تردد داشته). این الگو کاملاً چیز دیگری‌ست: یک *ستون کامل* (مثلاً یک عامل حقوقی خاص) را در **کل گزارش** پنهان می‌کند، چون هیچ‌کدام از کارمندهای انتخاب‌شده در این دوره برایش مقدار غیرصفر ندارند. نمونه‌ی واقعی و تأییدشده: گزارش «لیست حقوق کارمندان» (`SalaryList.rdl` + ساب‌ریپورت `SalaryListItems.rdl` — جزئیات کامل در `report-catalog.md` بخش ۵).

### ۳.۱ مکانیزم SQL: LEFT JOIN با شرط عضویتِ محدودشده + فیلتر `IS NOT NULL`

قلب این الگو یک لیست «کاندیدهای ستون» است (از یک جدول تنظیمات/View-Setting که تعیین می‌کند کدام عامل‌ها *ممکن است* دیده شوند) که با یک زیرکوئری «آیا این عامل، برای هر یک از کارمندهای انتخاب‌شده، در این دوره حداقل یک مقدار غیرصفر دارد؟» فیلتر می‌شود:

```sql
;WITH TitleCTE AS
(
    SELECT
        RowNumber = ROW_NUMBER() OVER (ORDER BY ViewSettingDetail.[Order]),
        Title     = FactorDef.Title
    FROM dbo.ViewSetting RC
    INNER JOIN dbo.ViewSettingDetail
        ON RC.ViewSettingID = ViewSettingDetail.ViewSettingRef

    LEFT JOIN dbo.FactorDefinition FactorDef
        ON ViewSettingDetail.FactorRef = FactorDef.FactorID
        AND FactorDef.FactorID IN (          -- ⚠️ نه INNER JOIN، نه یک WHERE جدا — این شرط داخل ON است
            SELECT DISTINCT FactValue.FactorRef
            FROM dbo.FactValue
            WHERE FactValue.Period = @Period
              AND FactValue.[Value] <> 0
              AND FactValue.EntityRef IN (SELECT EntityID FROM @SelectedEntities)
        )

    WHERE RC.ViewSettingID = @ViewSettingID
      AND FactorDef.Title IS NOT NULL          -- ⚠️ این‌جا حذف واقعی اتفاق می‌افتد
)
SELECT * FROM TitleCTE;
```

چرا `LEFT JOIN` با شرط داخل `ON` و نه `INNER JOIN` ساده یا `WHERE FactorRef IN (...)`؟ چون خودِ لیست کاندیدها (`ViewSettingDetail`) باید کامل خوانده شود تا ترتیب (`[Order]`) درست بماند؛ شرط «آیا داده دارد» فقط تعیین می‌کند که `FactorDef` روی هر ردیف `NULL` بشود یا نه. `WHERE ... IS NOT NULL` در انتها است که واقعاً ردیف‌های بدون داده را از خروجی حذف می‌کند. اگر مستقیم `INNER JOIN ... AND FactorRef IN (...)` بزنی هم همین نتیجه را می‌گیری (چون فقط ردیف‌های match می‌مانند)؛ تفاوت عملی کوچک است ولی الگوی `LEFT JOIN + IS NOT NULL` باعث می‌شود بتوانی بین «اصلاً در تنظیمات نیست» و «در تنظیمات هست ولی داده ندارد» دیباگ کنی (کافی‌ست موقتاً `IS NOT NULL` را بردار).

**نکته‌ی مهم برای پیاده‌سازی درست:** همین دقیقاً شرط «داده دارد» باید در کوئری‌ای که مقدار واقعی هر ستون را برای هر ردیف/کارمند حساب می‌کند هم تکرار شود (با همان `IN (SELECT ...)`) — وگرنه ممکن است دیتاست عنوان یک ستون را نشان دهد ولی مقدارش همیشه خالی باشد، یا برعکس. در گزارش نمونه، هر دو کوئری (کوئری عنوان‌ها و کوئری مقدارها) این زیرکوئری عضویت را جداگانه و عیناً تکرار کرده‌اند.

**دام رایج:** دامنه‌ی این زیرکوئری «آیا داده دارد» معمولاً *ساده‌تر* از فیلترهای کاملی‌ست که روی مقدار نمایشی اعمال می‌شود (مثلاً در نمونه‌ی واقعی، شرط «داده دارد» فقط بر اساس `IssueYearMonth = @Period` بود، بدون فیلترهای پیچیده‌ی معوقه/جاری که روی مقدار نهایی اعمال می‌شدند). این می‌تواند باعث شود ستونی نشان داده شود که در حالت نمایشیِ نهایی (بعد از فیلترهای دقیق‌تر) خالی باشد. **همیشه از کاربر بپرس** آیا «داشتن داده» باید دقیقاً همان فیلترهای نمایش مقدار را رعایت کند یا یک چک ساده‌تر و گسترده‌تر کافی است — این تصمیم را حدس نزن.

### ۳.۲ سرریز: وقتی تعداد ستون‌های دارای‌داده از تعداد جای فیزیکی ثابت بیشتر است

اگر گزارش فقط N ستون فیزیکی ثابت دارد (مثلاً ۷ تا) ولی بعد از حذف ستون‌های بی‌داده هنوز بیش از N عامل باقی مانده، باید نتیجه به چند «ردیف/بلوک» بعدی سرریز کند (نه این‌که مقادیر اضافه بی‌صدا گم شوند — برخلاف الگوی ۲ که سرریز را نادیده می‌گیرد، این‌جا باید همه‌چیز دیده شود):

```sql
ColumnIndex = ROW_NUMBER() OVER (ORDER BY [Order]) % @MaxColumnsPerBlock,   -- ۰ یعنی «آخرین جای بلوک»
BlockIndex  = ((ROW_NUMBER() OVER (ORDER BY [Order]) - 1) / @MaxColumnsPerBlock) + 1
```

سپس هر `BlockIndex` یک «ردیف عنوان» و یک «ردیف مقدار» جدا در خروجی می‌سازد (با یک فیلد `[Type]` مثل `'Title'`/`'Value'` که در Tablix با `Hidden` تفکیک می‌شود). **نکته‌ی ظریف:** ستون فیزیکی آخر (که `ColumnIndex = 0` می‌گیرد) همیشه «آخرین جای همان بلوک» را نشان می‌دهد، صرف‌نظر از این‌که `@MaxColumnsPerBlock` واقعاً چند است — یعنی اگر ادمین تعداد ستون‌های فعال را کمتر از حداکثر تنظیم کند (مثلاً ۵ به‌جای ۷)، همان ستون فیزیکی آخر معنایش عوض می‌شود (می‌شود «پنجمین» نه «هفتمین»). سمت RDL این پویایی را با یک زنجیره‌ی شرط `Hidden` مدیریت می‌کند — جزئیاتش در `rdl-tablix-structure.md` بخش ۶.

## ۴. پایپ‌لاین جدول‌های موقت برای گزارش‌های تردد/HR

الگوی رایج در گزارش‌های حضور و غیاب:
1. `#RawEvents` — فیلتر اولیه‌ی رکوردهای معتبر از جدول خام (مثلاً وضعیت تأییدشده).
2. `#ActiveAssignment` — آخرین تخصیص فعال هر کارمند (شیفت/گروه کاری) با `ROW_NUMBER() OVER (PARTITION BY EmployeeRef ORDER BY ... DESC) = 1`.
3. `#WindowedEvents` — اتصال رکوردهای خام به بازه‌ی زمانی شیفت هر روز (`DATEADD` با `StartTime`/`ExtraMinutesBefore` برای پوشش شیفت‌های شب که از نیمه‌شب رد می‌شوند).
4. جدول(های) تجمیعی نهایی (MIN/MAX یا ROW_NUMBER-pivot طبق نیاز).
5. `DROP TABLE IF EXISTS ...` در انتها برای پاک‌سازی — همه‌ی temp tableهای ساخته‌شده را لیست کن، حتی جدیدها.

همیشه در پایان کوئری کامل، لیست `DROP TABLE IF EXISTS` را چک کن — فراموش‌کردن یک temp table جدید در این لیست معمولاً باعث خطا در اجرای بعدی روی همان session نمی‌شود ولی نشانه‌ی بی‌دقتی است و بهتر است رعایت شود.

## ۵. تست مستقل از Report Builder

قبل از اینکه کوئری اصلاح‌شده را داخل RDL جاسازی کنی، همیشه نسخه‌ی مستقل و قابل‌اجرا در SSMS از آن بساز (با `DECLARE` برای پارامترها به‌جای اینکه از Report Builder بیایند) و به کاربر بده. این کار باگ‌های منطقی را زودتر و راحت‌تر از دیباگ در Report Builder پیدا می‌کند.
