# واژه‌نامه فارسی رسمی نرم‌افزار (Glossary)

این فایل، نقطه‌ی ورود به سه دیتاست جدیدی است که مستقیماً **از خودِ نرم‌افزار کاربر** (نه حدس Claude)
استخراج شده‌اند: عنوان فارسی جدول‌ها، فهرست کامل موجودیت‌های تعریف‌شده در کل نرم‌افزار، و مقادیر
فارسی Lookupها/Enumها. این‌ها **منبع درجه‌یک برای معنای تجاری (Persian title)** هستند — دقیق‌تر از
حدس زدن از روی نام انگلیسی ستون/جدول. همیشه قبل از حدس زدن معنای یک جدول/enum، این‌جا را چک کن.

⚠️ **این‌ها جایگزین مرحله‌ی ۰ (کوئری تشخیصی + نمونه‌داده) نیستند.** عنوان فارسی یک جدول یا یک مقدار
Lookup می‌گوید «این یعنی چه»، ولی نمی‌گوید «این ستون nullable است یا نه»، «چند درصد رکوردها این مقدار
را دارند»، یا «این fkid واقعاً همیشه پر است یا نه». برای این‌ها هنوز باید طبق قوانین طلایی SKILL.md
نمونه‌داده/توزیع واقعی بخواهی.

## فایل‌های موجود (در `references/glossary/`)

### ۱. `hcm3-table-titles.csv` — عنوان فارسی ۱۵۶ جدول HCM3
ستون‌ها: `Schema, Table, PersianTitle`
منبع: فایل اکسل «عنوان جداول سرمایه انسانی» که کاربر مستقیماً از تنظیمات نرم‌افزار گرفته.
فقط زیرمجموعه‌ای (۱۵۶ از ۴۶۱) از جدول‌های HCM3 را پوشش می‌دهد — عمدتاً حوزه‌های آموزش (Course*)،
احکام کارگزینی (Statute*)، ارتقا و ترفیع (Promotion*)، ساختار فایل بانکی (FileStructure*)، نوع
استخدام (EmploymentType*). **جدول‌های تردد/مرخصی خام (AttendanceData, LeaveRemainder, ...) در این
فایل نیستند** — آن‌ها از قبل در `known-database-schema.md` مستند شده‌اند.
مثال جست‌وجو:
```bash
grep -i "EmploymentType" references/glossary/hcm3-table-titles.csv
```

### ۲. `entity-catalog.csv` — فهرست کامل موجودیت‌های نرم‌افزار (۱۹۶۸ ردیف، همه‌ی ماژول‌ها)
ستون‌ها: `Code, Module, SubModule, TableName, PersianTitle, MappedSchema, IsTranslated`
منبع: «خروجی فرم اطلاعات موجودیت‌های تعریف‌شده در نرم‌افزار» — فهرست خودِ نرم‌افزار از موجودیت‌هایی
که برایشان فرم/UI تعریف شده (نه لزوماً همه‌ی ۳۴۲۸ جدول فیزیکی؛ فقط آن‌هایی که در لایه‌ی متادیتای
اپلیکیشن هم به‌عنوان Entity ثبت شده‌اند).
- `Module`/`SubModule` از تجزیه‌ی `نام کامل موجودیت` (مثل `SystemGroup.HCM.Staff,Employee` → Module=`HCM`,
  SubModule=`Staff`, TableName=`Employee`) به‌دست آمده — این **نام ماژول برنامه** است، نه لزوماً نام
  schema پایگاه‌داده.
- `MappedSchema` تلاش خودکار برای نگاشت `Module` به schema است، فقط برای مواردی که مطمئن بودیم:
  `HCM→HCM3, Financial→FIN3, Logistics→LGS3, FAM→FAM3, Procurement→PRC3, Budgeting→BDG3, FCC→FCC3, QCM→QCM3, ECM→ECM`.
  برای ۵۲۵ ردیف (ماژول‌هایی مثل `ReceiptAndPayment`, `Security`, `Workflow`, `ReportBuilder`,
  `EPayment`, `MetaData`, `FormBuilder`, ...) هنوز مشخص نیست دقیقاً کدام schema فیزیکی هستند — این‌ها
  می‌توانند بخشی از `FIN3`/`ACC`/`SYS3` یا schemaهای دیگر باشند. **قبل از استفاده از این ردیف‌ها برای
  یک گزارش واقعی، اول با `grep` در `schemas/<SCHEMA-حدسی>.md` چک کن که آیا جدولی با همین نام واقعاً
  آنجا هست، تا نگاشت schema را تأیید کنی.**
- `IsTranslated=0` یعنی عنوان فارسی واقعی برایش تعریف نشده (خروجی خام مثل
  `SystemGroup.ECM.ReminderManagement:Reminder_EntityName` است) — این ۱۶۰ ردیف را نادیده بگیر.
- کاربرد اصلی: وقتی گزارش جدیدی درباره‌ی ماژولی خارج از HCM3 (مثلاً مالی، انبار، دارایی ثابت) خواسته
  شد و آن schema هنوز کاوش نشده، **اول این فایل را برای گرفتن سرنخ نام فارسی جدول‌های مرتبط بگرد**،
  بعد Stage 0 را فقط روی همان جدول‌های مشخص‌شده اجرا کن (نه کل schema).
مثال جست‌وجو:
```bash
grep ",FIN3,1" references/glossary/entity-catalog.csv   # همه‌ی ردیف‌های ترجمه‌شده‌ی مالی
awk -F',' '$6=="LGS3" && $7=="1"' references/glossary/entity-catalog.csv   # انبار/لجستیک ترجمه‌شده
```

### ۳. `lookup-values.csv` — مقادیر فارسی Lookup/Enum (۳۳۲۷ ردیف، ۸ schema)
ستون‌ها: `LookupID, Schema, Type, PersianValue, OrdinalInType`
منبع: فایل «نامگذاری فارسی جداول اصلی» (نام فایل گمراه‌کننده است — محتوا در واقع **مقادیر Lookup**
است، نه اسم جدول). این جدول‌ها معمولاً پشت ستون‌های `*TypeCode`, `*StatusRef`, `*MeasurementUnit` و
مشابه هستند.
پوشش schema: `HCM3` (۲۸۶ نوع Enum!)، `SLS3` (۱۴۹)، `RPA3` (۱۲۵)، `FIN3` (۹۹)، `GNR3` (۷۵)، `PAC3` (۴۳)،
`CAC3` (۳۵)، `SYS3` (۱۵).
- `OrdinalInType` موقعیت هر مقدار در همان گروه `(Schema, Type)` به ترتیب ظاهرشدن در فایل خام است —
  **این یک حدس جهتی برای کد enum عددی است (۱، ۲، ۳، ...)، نه یک تضمین.** فایل منبع، خودِ کد عددی
  استفاده‌شده در ستون‌های دیتابیس را نمی‌دهد (`LookupID` یک PK سراسری در جدول Lookup سیستم است، نه
  کد enum محلی). **قبل از این‌که این ترتیب را در یک `CASE WHEN Code=1 THEN ...` واقعی به‌کار ببری،
  حتماً با `GROUP BY` روی همان ستون در دیتابیس واقعی (طبق قانون طلایی مرحله‌ی ۰) تأیید بگیر** —
  دقیقاً همان‌طور که پیش‌تر `AttendanceMeasurementUnit`/`MeasurementUnitCode` تأیید شد.
- **تأییدشده با داده‌ی واقعی موجود:**
  - `HCM3.AttendanceDataEntrance`: ترتیب ۱=«ورود»، ۲=«خروج» — هم‌راستا با فرض قبلی `Entrance` بیت
    (۱=ورود، ۰=خروج؛ چون این یک enum جدا برای UI است نه دقیقاً همان bit، فقط جهت را تأیید می‌کند).
  - `HCM3.AttendanceMeasurementUnit`: ۱=«عدد»، ۲=«روز»، ۳=«روز-ساعت-دقیقه»، ۴=«ساعت-دقیقه» — این
    دقیقاً `AttendanceFactor.MeasurementUnitCode=4` را که در `known-database-schema.md` به‌عنوان
    «مقدار به دقیقه، نمایش HH:mm» مستند شده بود، تأیید می‌کند.
  - `HCM3.AttendanceStatusType`: در فایل به‌ترتیب «مجوز حضور، تردد، مرخصی، ماموریت» آمده، ولی
    برخلاف دو مثال بالا، `LookupID`های این گروه پیوسته نیستند (`6881` سپس `1207-1209`) — یعنی
    ترتیب ظاهرشدن در فایل احتمالاً ترتیب واقعی کد enum را نشان نمی‌دهد. این مثال دقیقاً همان درسی
    است که این بخش می‌خواهد بدهد: حدس‌زدنِ کد از روی ترتیب فایل خطرناک است.
    **✅ به‌روزرسانی: `AttendanceStatusRef` در `HCM3.AttendanceData` دیگر مبهم نیست** — با
    `SELECT * FROM hcm3.AttendanceStatus` (جدول Lookup واقعی، نه این فایل CSV) تک‌تک ۱۷ مقدار و
    عنوان فارسی‌شان تأیید شد (`2`=«حضور»، `6`-`13`=انواع مرخصی، و غیره). جدول کامل و ماجرای کشفش
    (شامل یک باگ واقعی که همین حدس‌نزدن رفعش کرد) در `known-database-schema.md` بخش «جدول‌های
    تردد خام» است — همیشه از آن‌جا بخوان، نه از این فهرست چهارتایی.
مثال جست‌وجو:
```bash
grep ",HCM3,MissionTypeCode," references/glossary/lookup-values.csv
awk -F',' '$2=="HCM3"' references/glossary/lookup-values.csv | cut -d',' -f3 | sort -u   # فهرست کل انواع Enum در HCM3
```

## قانون استفاده در مرحله‌ی ۰ (Stage 0)

ترتیب کامل چک‌کردن در `SKILL.md` مرحله‌ی ۰ است (این فایل جایگاه چهارم آن ترتیب را دارد).
هرگز یک عنوان فارسی از glossary را به‌تنهایی برای نوشتن منطق نهایی گزارش کافی ندان — این‌ها سرنخ
هستند تا مرحله‌ی ۰ سریع‌تر و هدفمندتر انجام شود، نه جایگزین اثبات با داده‌ی واقعی.

## به‌روزرسانی آینده

کاربر قصد دارد به‌تدریج فایل‌های بیشتری از این نوع (عنوان فارسی جدول‌های سایر schemaها مثل FIN3،
LGS3، FAM3) بفرستد. هر بار فایل جدیدی رسید:
- اگر همان ساختار (Schema/Table/Title) را دارد → یک CSV جدید هم‌نام schema در همین پوشه اضافه کن
  (مثل `fin3-table-titles.csv`) و همین فایل را با یک خط توضیح جدید به‌روزرسانی کن.
- اگر ساختار متفاوت است (مثلاً ستون‌های دیگر) → اول ساختارش را با کاربر تأیید کن، بعد تصمیم بگیر آیا
  به یکی از سه فایل موجود اضافه می‌شود یا فایل نوع جدیدی لازم است.
- بعد از هر افزودن، این‌جا و `database-module-map.md` (ستون «معنای تجاری») را هم‌زمان به‌روز کن.
